# RE-CAP Demo PoC 결론

RE-CAP Demo는 스크린샷을 최대 20장 선택해 iOS 온디바이스 OCR로 텍스트를 추출하고, 룰베이스로 저장 목적 컬렉션을 분류하는 기술 검증 앱이다.

이 PoC의 목적은 실제 서비스 구현 전에 다음 질문에 답하는 것이었다.

1. iOS에서 사용자가 선택한 스크린샷을 안정적으로 OCR 처리할 수 있는가?
2. 20장 단위 배치 처리 시간이 사용자에게 허용 가능한가?
3. 백그라운드 OCR 처리가 핵심 플로우로 필요한가?
4. LLM 없이 룰베이스만으로 기본 컬렉션 분류가 가능한가?
5. `확인 필요` 플로우를 제품 UX로 가져갈 가치가 있는가?

---

## 최종 결론

### 1. 로컬 OCR은 PoC 기준으로 사용 가능하다

- Apple Vision 기반 온디바이스 OCR로 스크린샷 텍스트를 추출할 수 있었다.
- 데모 기준 20장 처리 시간이 약 12초 수준으로 관측되어, MVP 초기에는 서버 OCR 없이도 기본 검증이 가능해 보인다.
- 서버 호출이나 LLM 생성이 추가되면 시간이 늘 수 있으므로, 이후에는 서버 비동기 job 또는 진행 상태 UX를 함께 설계해야 한다.

### 2. 백그라운드 OCR은 핵심 플로우에서 제외하는 것이 적절하다

초기에는 iOS 26 `BGContinuedProcessingTask`를 이용한 백그라운드 처리를 검토했지만, PoC 결론은 다음과 같다.

- 20장 기준 처리 시간이 길지 않아 백그라운드 실행의 제품적 효용이 크지 않다.
- iOS 백그라운드 실행은 사용자의 기대처럼 “앱을 닫아도 안정적으로 계속 처리”되는 모델이 아니다.
- 강제 종료, 시스템 만료, 권한/상태 변화에 따라 중단될 수 있어 핵심 UX로 삼기에는 리스크가 크다.

따라서 MVP 기본 정책은 다음으로 정리한다.

```text
앱을 열어둔 상태에서 foreground batch 처리
→ 진행률 표시
→ 완료 후 결과 저장
```

백그라운드 처리는 정식 제품의 핵심 플로우가 아니라, 서버 비동기 처리나 재개 가능한 job 구조가 생긴 뒤 다시 검토한다.

### 3. 룰베이스 분류는 MVP 초기 전략으로 가능성이 있다

PoC에서는 OCR 텍스트를 기반으로 4개 기본 컬렉션을 룰베이스로 분류했다.

- 비교할 후보
- 챙겨야 할 정보
- 남겨둘 기록
- 참고할 자료

초기 구현의 `분류하기 어려움` 비율이 높았기 때문에, 최종 방향은 다음으로 수정했다.

```text
룰 근거가 있으면 최선의 컬렉션을 제안한다.
확신이 낮으면 “미분류”가 아니라 “확인 필요”로 보낸다.
```

즉 `unclassified`를 별도 컬렉션처럼 쓰기보다, 내부 상태로 `needsReview`를 두는 것이 제품적으로 더 적합하다.

### 4. `확인 필요`는 실패 상태가 아니라 검수 상태다

RE-CAP의 핵심 UX는 AI 또는 룰이 만든 정리 결과를 사용자가 최소 행동으로 승인·수정·삭제할 수 있게 하는 것이다.

따라서 확인 필요 상태는 다음 의미로 정의한다.

> 자동 정리 결과가 충분히 명확하지 않을 때, 사용자가 최종 저장 상태를 한 번 확인하고 저장하거나 삭제하는 최소 보정 플로우

확인 필요로 가는 대표 이유:

- 컬렉션 분류 확신이 낮음
- 제목 생성 실패 또는 품질 낮음
- 요약 생성 실패 또는 품질 낮음
- OCR 텍스트가 부족함
- 서로 다른 컬렉션 신호가 충돌함

중요한 점은, 확인 필요는 “분류 실패”가 아니라 “저장 전 확인 필요”라는 점이다.

## 제품 방향 제안

### 기본 처리 UX

현재 성능 기준으로는 foreground 처리가 적합하다.

| 처리 시간 | 권장 UX |
| --- | --- |
| 1~3초 | 일반 로딩 |
| 3~10초 | 화면 내 진행 상태 표시 |
| 10~20초 | progress bar + `n장 중 m장 완료` |
| 20초 이상 | 취소 가능, 부분 결과 저장, 재개 고려 |

MVP에서는 다음 문구 수준으로 충분하다.

```text
20장 분석에 약 10~15초 걸립니다. 앱을 열어둔 상태에서 진행해주세요.
```

### 분류 UX

권장 구조:

```text
정리 완료
- 컬렉션 확신 높음
- 제목/요약/컬렉션 생성 완료

확인 필요
- 최선의 컬렉션 제안은 있음
- 다만 확신 낮음 또는 제목/요약 보정 필요

처리 실패
- OCR/이미지 분석 자체가 실패
- 재시도 또는 삭제 필요
```

피해야 할 구조:

```text
분류하기 어려움 컬렉션에 저장
```

권장 구조:

```text
status = needsReview
suggestedCollection = reference
reviewReasons = [.collectionLowConfidence]
```

### 룰 엔진 운영 방향

초기에는 Swift 코드에 룰을 직접 넣어도 되지만, 제품화 단계에서는 룰을 데이터화하는 것이 좋다.

예시:

```yaml
- id: reservation_number
  category: actionRequired
  patterns:
    - 예약번호
    - 예매번호
    - reservation number
  weight: 5
  reviewThreshold: strong

- id: receipt_payment
  category: record
  patterns:
    - 영수증
    - 결제 완료
    - 승인번호
  weight: 5
```

룰에는 최소한 다음 속성이 필요하다.

- `id`
- `category`
- `patterns`
- `weight`
- `negativePatterns` 또는 제외 조건
- `examples`
- `memo`
- `version`

향후에는 실제 스크린샷 평가셋을 만들고, 룰 변경 전후를 비교해야 한다.

권장 초기 지표:

```text
needsReview 비율: 10~25%
unclassified/분석불가 비율: 10% 이하
전체 분류 정확도: 75% 이상
핵심 컬렉션 precision: 80% 이상
```

## 데모 앱 구현 요약

현재 데모 앱은 다음을 포함한다.

- SwiftUI 기반 iOS 앱
- PhotosPicker 기반 이미지 선택
- 최대 20장 제한
- Vision OCR 처리
- 이미지별 OCR 시간 측정
- 전체 배치 시간 측정
- 룰베이스 컬렉션 분류
- 낮은 확신 표시
- 실험 결과 로컬 JSON 저장
- JSON/CSV 내보내기
- 백그라운드 처리 실험 코드

백그라운드 처리 코드는 PoC 흔적으로 남아 있지만, 최종 제품 방향에서는 핵심 플로우에서 제외하는 것을 권장한다.

## 빌드 방법

```bash
xcodebuild \
  -project Recap-demo.xcodeproj \
  -scheme Recap-demo \
  -destination 'generic/platform=iOS' \
  -derivedDataPath ./.derivedData \
  CODE_SIGNING_ALLOWED=NO \
  build
```

## 다음 단계

PoC 이후 제품화 단계에서 우선 검토할 항목은 다음과 같다.

1. 백그라운드 OCR 옵션 제거 또는 실험 기능으로 격하
2. `분류하기 어려움`을 컬렉션이 아니라 `확인 필요` 상태로 재정의
3. 제목/요약/컬렉션을 포함하는 `정리 결과` 데이터 모델 설계
4. 룰셋을 Swift 코드에서 JSON/YAML 리소스로 분리
5. 실제 스크린샷 100~300장 평가셋 구축
6. 룰 변경 전후 정확도와 확인 필요 비율 측정
7. LLM은 기본 분류기가 아니라 제목/요약 생성, fallback, 오분류 분석 보조로 우선 검토

## 최종 판단

이 PoC를 통해 RE-CAP MVP의 기본 방향은 다음으로 정리한다.

> RE-CAP은 앱을 열어둔 상태에서 빠르게 스크린샷을 OCR 처리하고, 룰베이스로 최선의 컬렉션을 제안한다. 자동 정리 결과가 명확하면 바로 정리 완료하고, 애매하면 미분류로 버리지 않고 `확인 필요` 상태로 보내 사용자가 최소 행동으로 저장 또는 삭제하게 한다.

즉 MVP의 핵심은 백그라운드 실행이나 완전 자동 AI가 아니라,

```text
빠른 foreground 정리
+ 설명 가능한 룰베이스 분류
+ 확인 필요 검수 플로우
```

이다.
